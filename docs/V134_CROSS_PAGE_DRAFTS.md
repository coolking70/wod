## v123原偶发失败已经复现并定位

先在相同390px上下文跟踪input/change、写入调用栈、读取值和storage通知。12次精简检查（普通CPU、4/8倍降速各4次）均通过，不能据此解释原失败。随后按原v123完整流程与v124并行重放3轮，其中v123两次精确复现`2 !== 888`，v124均通过。

两次失败都记录到：写入页在完整加载后收到change，`setItem`写888，change冒泡时本页读值也为888；原断言在读取页立即读到2，而随后该页收到的storage通知及当时读取都已是888。读取页除启动写2外没有后续覆盖写。由此排除“change未处理/写入失败”和所测流程中的“旧页后来写回2”；原验收把**写入页的同步完成**误当成**另一页缓存已经传播完毕**。

修复在`scripts/browser-storage-sync.cjs`与v123验收，运行代码不为这项时序问题延时或反复写入：

1. 在写入前监听读取页对应键的真实localStorage通知。
2. 正常操作写入页，立即严格断言它的完整公会/配置及种子888。
3. 等待对应新原文的通知，再执行原读取页种子888、整份数据相同和拒绝陈旧收藏载入的断言。
4. 恢复旧种子也等待相应通知，新增完整原始两键恢复断言；监听器显式移除。

没有固定sleep、伪造事件/写值、容许2或删除断言。修正后原v123/v124并行完整重放3轮共6次通过。前后原失败与跟踪收据分别保留，不改写v133“当时未定位”的历史记录。有限重复不能证明所有浏览器永远无偶发问题，但本次同症状有写入和通知链证据，已超出仅靠重跑通过的推测。

[WHATWG Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface)正文明确远端通知按任务派发，跨agent cluster交互不作锁保证。[Chromium CachedStorageArea源码](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/storage/cached_storage_area.h)说明本地映射缓存通过异地变更回调更新；这与当前Chromium实测路径一致。源码引用的是公开main的机制说明，不冒称已逐字审计安装二进制。标准本身不要求每次跨页立即读取都旧；两次具体旧读由本轮跟踪证明。

这是针对可见更新的快照比较，不是跨进程锁、服务端权威或真正同时写入的事务保证。收到通知前各页仍可能暂时有不同缓存，不能将本功能包装成多人存储协议。没有新存档字段、迁移、账号后端或权限设置。
