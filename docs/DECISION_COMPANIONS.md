# 已确认：小规模招募名册

2026-11-01：用户选择招募方案。v0.39 已交付，见 V39_ROSTER.md。以下保留决策背景。

已确认的“个人英雄＋托管伙伴”保持不变。v0.38 已实现个人反馈、证据定位、伙伴职责预览与实际出征闭环。下一阶段将扩展可培养的队伍内容，需要确定伙伴是否固定。

## 方案一：小规模招募名册（推荐）

主角单独培养，每次选择五名伙伴出战；首批只增加两名候补，避免一次铺开大量角色。伙伴仍以职责预设管理，高级编辑保留。装备和成长归具体伙伴，离队不丢失资产。

实施顺序：
1. 拆分角色实例ID和职业模板ID，移除固定a–f角色索引假设；更新战斗、支援追踪、存档和配置校验。
2. 加入名册与五个伙伴出战槽位，明确同职业成员的区分、装备归属和出征快照。
3. 增加两名候补及招募入口，再制作能体现替补价值的地下城遭遇。
4. 保持以主角为中心的入口，不要求逐个管理所有伙伴才能出征。

价值：队伍组成也成为战前策略，允许替换职责组合，更接近WoD式队伍协作的构筑需求。代价：需要较大的角色模型调整，阵容平衡与养成界面复杂度上升。

## 方案二：固定五名长期伙伴

沿用当前六人中的一名主角与其余五名伙伴，通过职责、装备与职业进阶改变分工，不引入候补或出战替换。

实施顺序：深化六个职业的进阶分支；增加伙伴专属事件、任务与协作技能；按固定队伍能力设计后续章节。

价值：个人和伙伴的长期身份更清晰，操作负担较低，能更快扩展剧情章节。代价：队伍组成变化少，多样性主要依赖技能与装备；不能把它描述成自由组队系统。

## 为什么现在需要选择

当前角色ID同时代表个人与职业，并且存档要求恰好六名成员。招募替换需要先修改这一核心模型，再制作新伙伴；固定伙伴则应将投入放在专属成长和章节内容。两者不是调整几项数值就能互换的开发顺序。

两种方向都保持本机公会、个人主角和伙伴托管，不要求账号、在线多人或旧存档兼容。当前发布版维持六名角色，等待选择后再进入上述分支。
