# v0.19 治疗决策诊断

引擎在有治疗技能角色的实际普通行动机会开始时记录快照，并将healingDecision附加到该次行动的既有施放、道具、等待或失败事件。字段schema=1；不新增事件、不改变事件ID、行动ID或随机调用。配置和结算ruleset保持0.14.0。

## 记录内容

记录自动治疗开关、范围、阈值、行动开始MP与药草、所需资源、同阵营正式成员及召唤物的生命比例和资格。按原规则筛选范围内存活伤员，按生命比例升序选择；同值保留原单位顺序。资格分为倒下、范围外、满生命、高于阈值或满足阈值。最低比例候选不等于一定执行治疗：开关、阈值与资源会阻止执行。

实际使用随身道具后标记item_priority，说明道具占用行动、未进入治疗检查；不展示候选表作为实际治疗选择。治疗关闭时表格仅为状态快照，界面说明未执行选择。其他状态包括无目标、未达阈值、缺蓝、缺药草、满足条件及实际治疗。死亡或战斗提前结束导致未轮到行动时，没有该行动记录；不伪造“已检查”。

结果附着到实际执行事件。成功治疗核对真实heal事件；缺料/缺蓝沿用原来的skip与普通指令回退。决策记录与角色快照独立复制。诊断读取不消耗随机数或资源。

## 界面

受击与救护时序和单次施放详情展示决策卡。守灯原始队形种子1第三房第二回合：露弥35/110（31.8%）、维斯9/102（8.8%），MP29、药草6，阈值65%，全队范围；因此按最低比例规则治疗维斯。并非缺料，也不是露弥不满足阈值。

## 验证

129项测试通过。新增覆盖阈值等号、资源优先级、治疗开关、范围排除、倒下/满血、同生命比例顺序、不可变快照、实际治疗对象/费用与道具优先。原始守灯种子1药师没有使用药瓶，因此道具测试显式设置低MP初始状态来触发实际道具分支。

另使用改动前引擎（git HEAD版本）对基线、断潮、守灯三种配置分别跑种子1/3/731，共9场：去掉healingDecision后整个返回战报深度相等，包括事件、投点、快照、统计与结算。临时旧引擎文件已删除。浏览器验证候选表、实际治疗对象及回退时无未来数据。

## 下一步

诊断已经具备解释现有治疗取舍所需的基本证据。后续应优先让玩家根据这些证据改配置，例如增加明确的治疗优先策略及单变量对照，而不是继续堆叠只读面板；任何策略扩展都应单独版本化规则与回归结果。
